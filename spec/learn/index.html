What is a cart?

A plain object, compiled to bytes, shipped as a URL

A cart is a JS object — palette, entities, sprites, tiles, an optional generated map, and up to six small bytecode programs called hooks. encodeCart() turns it into a compact byte array; that gets base64url-encoded (and usually deflate-compressed) into a URL fragment. Paste that fragment into the runtime and it plays — the fragment is the game, nothing is fetched from a server.

Anatomy of a cart

Palette, screen, entities, sprites & tiles

The header sets a fixed screen size and a palette of exactly 16 colors, generated — never hand-picked per color — from 8 bytes (paletteParams). Everything else visual (entities' sprites, the map's tiles) is built from indices into that same 16-color palette. Full field-by-field reference: cart-object.md.

Entity types

Every entity has 8 base props plus however many extra (extFieldCount) its type declares. The runtime owns four of the eight: [0]/[1] are x/y, [4] is its type id, [7] is its own entity id — all auto-managed. [2], [3], [5], [6], and anything from [8] up are free for the cart to define.

The VM

A small stack machine, no subroutines

Hook bytecode runs on a stack machine: push values, pop them into an operation, push the result. There is no CALL/RET — only JMP/JZ/JNZ to fixed labels. Every hook call is capped at 20,000 dispatched instructions (MAX_STEPS); going over sets a cart fault and stops the hook. Full table with exact stack order for every op: opcodes.md.

Entities & hooks

Six hooks, three different dispatch models

A cart's behavior lives in up to six bytecode blobs. They don't all run the same way — some are global (once per tick), some run once per entity, one runs once per colliding pair, and one runs at render time instead of simulation time. Full dispatch details: hooks.md.

self / a / b

  • on_init, on_input, on_frame: none bound
  • on_tick: self = that entity
  • on_collide: a/b = the pair, order not guaranteed
  • on_draw: self = the drawing entity

Budget

Every single call above — each entity's own on_tick, each pair's on_collide, each frame's on_draw — gets its own fresh 20,000-instruction budget, not a shared one.

Map generators

Three generators, one shared contract

A cart can ask for a generated tile grid instead of hand-placing a backdrop: a turtle-graphics track, a cellular-automata cave, or a token-stream platform level. All three return the same shape — a grid of tile ids plus a checkpoints list a hook can query with GET_CHECKPOINT. Token vocabularies and config fields: map-generators.md.

Sharing a cart

Bytes → base64url → a link

encodeCart() writes a tight byte layout (u8/u16/f32 fields in a fixed order, no padding) — see binary-format.md for the exact sequence. Those bytes are opportunistically deflate-compressed (kept only if actually smaller), then base64url-encoded straight into the URL fragment, tagged z. (compressed) or r. (raw) so the runtime knows which to reverse. If the cart has a name/author they ride in front as plain readable text: #name,author,z.….
